# Nonstop Example

Reference project generated by nonstop_cli.

A Flutter mono-repo generated by [nonstop_cli](https://pub.dev/packages/nonstop_cli):
one native Dart workspace, managed with Melos. This file is the contract for any
agent (or person) changing this repository. Before editing, read the nested
`CLAUDE.md` files on the path to what you change: the area (`apps/`,
`features/`, `packages/`, `plugins/`) and then the member itself (for example
`features/auth/CLAUDE.md`). Every app, feature, package and plugin has one.

## Repository map

| Path | Responsibility | May depend on |

| `apps/nonstop_example/` | Composition root: `main.dart`, `bootstrap.dart`, app router, splash | features, packages |

| `plugins/*` | Native platform integrations | nothing above them |
| `tool/check.dart` | Format + analyzer gate over every `lib/` and `test/` | - |
| `tool/coverage.dart` | Runs every suite, merges LCOV, requires 100% line coverage | - |
| `docs/architecture.md` | SOLID boundaries, failure and privacy policy | - |
| `.claude/skills/` | Task playbooks: `melos-workspace`, `new-feature`, `flutter-best-practices`, `design-system`, `troubleshooting` | - |

Dependencies point **inward**: app -> features -> packages -> plugins. An import
that points the other way is a design error, not a shortcut. Fix the boundary.

## First-time setup

Requires Flutter **3.47.5 or newer** (`flutter --version`). With FVM: `fvm use 3.47.5`.

```sh
dart pub get                  # resolves the whole workspace, one pubspec.lock
dart run melos bootstrap      # links members, IDE config
```

Optional, for Firebase-backed modules (the app boots without it):

```sh
dart pub global activate flutterfire_cli
cd apps/nonstop_example && flutterfire configure
```

## Run

```sh
cd apps/nonstop_example
flutter run --dart-define=BASE_URL=https://api.example.com
flutter run --dart-define=USE_EMULATORS=true   # Firebase emulator suite
```

Every environment value is a `--dart-define` declared in
`packages/core/lib/constants/environment.dart`. Never call
`String.fromEnvironment` anywhere else.

## Strict rules

These are boundaries, not suggestions. If a task seems to require breaking one,
stop and say so instead of working around it.

1. **Dependency direction.** Never import an app from a feature/package, or a
   feature from another feature. Features talk through contracts in `packages/`
   or through routes.
2. **SOLID, concretely.** One reason to change per class; extend by adding an
   implementation of a contract, not by editing consumers; small role
   interfaces over fat ones (contracts are `abstract interface class`;
   `GlobalEventType`, `NetworkException`, `NetworkResponse` and
   `NetworkApi` are base classes meant to be extended); business logic takes
   its collaborators through the constructor. `di.get` is allowed only at
   composition edges (bootstrap, `init()` functions, router, top-level widgets).
3. **No speculative code.** No interface with a single implementation unless it
   crosses a package boundary or needs a test fake. No "for later" scaffolding.
4. **Generated files are read-only.** Never hand-edit `*.g.dart`,
   `*.freezed.dart`, `*.i69n.dart` or `packages/design_system/lib/generated/`.
   Edit the source and regenerate. A hook enforces this.
5. **User-facing text goes through localization.** Add keys to
   `packages/localization/lib/messages.i69n.yaml`, regenerate, use `strings.*`.
   No string literals in widgets.
6. **Colors, typography and spacing come from the design system.**
   `Theme.of(context)` roles and `design_system` components; no raw
   `Color(0x...)` or font sizes. Load the `design-system` skill before any UI
   work.
7. **Every package has tests, and coverage stays at 100%.** The gate fails a
   package with no tests. Tests never hit the network or a real Firebase
   project; inject fakes against the same contracts.
8. **Errors stay typed.** Throw/return the typed exceptions of the owning
   package; never swallow an error silently or turn a failure into a success
   value. Log through the injected `Logger`, never `print`.
9. **Secrets never land in git.** No API keys, service-account files or
   tokens in source. `firebase_options.dart` holds public client config only.
10. **Do not bump versions or edit CHANGELOGs by hand**, and do not commit
    `pubspec_overrides.yaml` or build output.

Flutter-level practices (widgets, state, async, performance, accessibility,
testing) are in the `flutter-best-practices` skill; visual rules are in the
`design-system` skill. Load both before writing UI.

## Definition of done

A change is complete only when all of these hold. Report any you did not run.

1. `dart run melos run lint` passes.
2. `dart run melos run coverage` passes (100% line coverage, no missing tests).
3. New behavior has tests for success, invalid input, failure and cleanup.
4. Docs that describe the change are updated in the same change: the member's
   `CLAUDE.md` and `README.md`, or this file when a rule or command changed. A
   new member ships with its own `CLAUDE.md`.
5. The app still runs: `flutter run` (or `flutter build web` from the app).

Never describe a check as passing unless you ran it in this session.

## Communicating with the USER

These rules govern chat replies. Code, comments, commit messages and docs stay
as thorough as the rest of this file asks.

### Every answer ends with what the USER has to do (always)

- **Group by topic.** A heading per topic, bullets under it. Never one long run
  of prose.
- **Close with `What I need from you:`**: a short list of actions, or the single
  word `Nothing`. If the USER has to re-read the answer to work out what they
  are being asked to do, the answer failed.
- **Ten lines per topic, hard cap.** Longer means it is two topics, or detail
  nobody asked for.
- **Do not re-explain what the USER already knows.** They were in the
  conversation. Skip the recap and background; give the new fact.
- **A correction is one line**, and it comes first: "I was wrong about X; the
  truth is Y." Not a paragraph about how the mistake happened.
- **No narrating the investigation.** Give the finding, not the route to it.

Length is not thoroughness. Simple, clear, no noise, a clear action.

### Always recommend, and say what it costs (always)

Never hand over a list of options and stop; that moves the decision back to the
USER with none of the work done. Every set of options ends with a pick:

- **Which one, in one line.** Not "it depends", not two co-favourites.
- **Why: the reason, not the restatement.** "Because correctness beats
  cosmetics here" is a reason. "Because it fixes the bug" is the option
  repeated back.
- **What it costs:** time, risk, what stays broken meanwhile, who it blocks.

**When the quick fix and the right fix differ, give both and say so:**

- **The patch:** what to do now, how long, and exactly what it leaves unfixed.
- **The proper fix:** what it takes, and what it buys that the patch does not.
- **Which one today, and whether the other needs a ticket.** A patch shipped
  with no ticket for the real fix is a decision to never fix it; name it as such.

Example: a screen shows a raw exception string to users. Options: add a
`try/catch` in that one widget (ten minutes, every other screen still leaks);
map the error to a typed exception in the owning package and render it with
`DefaultErrorView` (an hour, fixes every caller); or rewrite error handling
app-wide (days, no extra user value). Pick: the typed exception in the package,
because the widget patch hides the defect in one place and leaves it
everywhere else.

If there is genuinely one sane option, say so, and say why the alternatives
are not alternatives. Silence reads as "I did not think about it".

### Check before you conclude (always)

Never name a cause you have not verified. In this repo the checks are cheap:
`git status` / `git diff`, `grep` for callers, `flutter test` on one package,
`dart run melos run lint`, `dart run melos run coverage`, and the app's logs
from `flutter run`. If a claim can be checked, check it before saying it, not
after the USER pushes back.

- **Look at the specific case, not the aggregate.** "Coverage is 100% overall"
  says nothing about the one file you changed. Read its uncovered-lines output.
- **Measure over a window longer than the thing you measure.** A retry, timer
  or refresh that fires every N seconds needs a test or observation longer than
  N before you call it fixed.
- **Read the code path before blaming it.** Before saying "this has no guard",
  grep for its callers; the guard is often one level up.
- **A sample proves what it contains, never what it lacks.** Five screens
  without a hard-coded color does not mean the repo has none. To claim
  absence, search the whole population (`grep -r` over `lib/`).
- **Do not generalise a diff from the lines you read.** To claim a change is
  formatting-only, run `dart format` on both versions and compare, or strip
  whitespace and diff. `git diff -w` cannot prove it: it does not collapse
  line breaks.
- **Check whether the defect is yours** before reporting it as pre-existing.
  `git status` and `git diff` answer that in one command.

Underneath all six: **say what would make the claim false, then go and look
for that.** When something cannot be verified, say so and say what would
settle it: "I think X; the way to know is Y."

### Do not make the USER connect the dots (always)

- **No cross-referencing.** No "as in option B above", no "like the earlier
  case". If a fact matters here, state it here, in full.
- **No ticket or PR numbers as shorthand.** Say what it was, then the number if
  it is still useful.
- **One decision per question.** Combine related findings yourself and give the
  conclusion; do not hand over five facts to assemble.

### Chat replies: short, bullets, no noise (always)

- **Bullets by default.** Prose only when a bullet genuinely cannot carry it.
- **Lead with the answer:** the finding, number or verdict on the first line.
- **One line per point.** Three sentences means two points, or unrequested detail.
- **Cut the reasoning unless asked.** The why belongs in the code comment and
  commit message; do not restate it in chat.
- **No recaps**, no re-listing what was agreed, no "so in summary".
- **Asking a question:** the question, then the options. No preamble.
- **Gotchas stay.** A "watch out" is never noise: keep it, one line, at the end.

### Explain in plain English (always)

- Lead with what something **does**, not what it **is**. "This shows a retry
  button when loading orders fails" beats "This emits `OrdersFailed` from the
  `OrdersCubit`."
- No jargon, framework names or acronyms unless unavoidable. Write for a smart
  person who does not write code every day.
- Use a concrete example or analogy when something is abstract.
- Call out any gotcha or known bug explicitly, at the end, in plain terms.
- Tables are fine for mappings and comparisons. In documents and code comments,
  group points or write prose instead of bullet walls; in chat, bullets win.

**For bugs and review findings, explain before coding in six parts:**

1. **Issue:** what is wrong, in one or two plain sentences.
2. **Solution:** what we will do, in similarly plain words.
3. **Impact:** what breaks today, what data is lost, what the user sees.
4. **Example:** a short timeline or a tiny broken-vs-fixed snippet.
5. **Changes needed:** files, new classes, migrations, rough size.
6. **Recommendation and why:** the pick or order, with a one-line reason.

Once the USER picks, go straight to code.
